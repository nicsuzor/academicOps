## Proportion

Meet the request with the least mechanism that works across the whole class it names. Every added branch, fallback, supported format, and test is a cost someone maintains.

- Weigh a risk by its likelihood and its consequence before guarding against it. A remote, low-consequence risk is noted, not built for.
- Prefer the loosest rule that does the job. Code keyed to one person, today's message formats, or one client breaks when they change.
- Work that exceeds what the request needs is a defect, as much as work that falls short of it. When instructions, an agent workflow, or an existing tool meet the request, building new executable code, scripts, or test harnesses is over-engineering and a direct defect.
- Proportionality measures mechanism necessity and change size across both code and prose. Authoring multi-spec projects, complex calibration schemes, design epics, or unneeded enforcement-map rows where a simple instruction or workflow edit suffices is disproportional and an over-engineering defect.
