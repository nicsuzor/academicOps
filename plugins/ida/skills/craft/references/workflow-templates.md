# Workflow Templates

Workflow templates (`type: template`, target 30-60 lines, hard ceiling 100 lines) govern repeatable multi-stage execution and task composition.

## Tier Placement

Universal plugin templates cover domain-independent processes applicable across any project. Project-specific or user-specific workflows belong in project (`project: <slug>`) or user PKB workflow tiers rather than universal plugin templates.

## Schema

```yaml
---
title: <human name>
type: template
description: <one line: what class of work this covers, so a composer can select it>
tags: [...]
---
```

## Invariants

- **Contract over neighbour**: Define input and output contracts per stage. Never name or chain to another template slug in frontmatter or body. A composite lists stages as ordered contract expectations (e.g., "an independent review verdict on the spec"), never as slugs; composing agents select matching templates at run time.
- **Headless execution and approval boundaries**: A step never pauses, waits, or prompts the user mid-task. Where approval is required, the step ends there: the worker files the complete artifact on the record and leaves downstream work blocked until approval is recorded (e.g., releasing as `partial` with a dependency-wired review or decision boundary). Cut the composition chain at that boundary; post-decision work belongs in a separate dependent task.
- **Promise only executor deliverables**: Output contracts specify only artifacts and state generated by the executing agent. Future external decisions or approvals are never executor deliverables.
- **`wf-` prefix**: Templates stating an obligation that blocks acceptance rather than a process that proceeds conventionally carry a `wf-` prefix.
