# Workflow Templates

Workflow templates (`type: template`, target 30-60 lines, hard ceiling 100 lines) govern repeatable multi-stage execution and task composition.

## Tier Placement

Universal plugin templates cover domain-independent processes applicable across any project. Project-specific or user-specific workflows belong in project (`project: <slug>`) or user PKB workflow tiers rather than universal plugin templates.

## Schema

```yaml
---
title: <human name>
type: template
description: <one line: what class of work this covers, so a composer can select it>
tags: [...]
---
```

## Invariants

- **Contract over neighbour**: Define input and output contracts per stage. Never name or chain to another template slug in frontmatter or body. A composite lists stages as ordered contract expectations (e.g., "an independent review verdict on the spec"), never as slugs; composing agents select matching templates at run time.
- **Headless execution and approval boundaries**: A step never pauses, waits, or prompts the user mid-task. User direction counts as approval outside external-audience, unruled-merge, unbounded-cost, or explicit user-hold boundaries -- never add class-based approval holds. Only where such an approval boundary applies does the step cut the composition chain there: the worker files the complete artifact on the record and leaves post-decision work in a separate dependent task (`needs`) blocked until approval is recorded (e.g., releasing as `partial` documenting the pending decision).
- **Promise only executor deliverables**: Output contracts specify only artifacts and state generated by the executing agent. Future external decisions or approvals are never executor deliverables.
- **Minimal by default**: State only the obligations the class of work truly needs. No review, sign-off, verification theatre, approval ceremony or safety step in a work template: handed-back work is reviewed separately. No step delivers anything to the user.
- **Tests only where they belong**: Require a test only for code that executes in a repository that already keeps a test suite; never for docs, instruction text or config, or where a repository has no tests or forbids them.
- **Fit the executor**: A `Worker:` template needs no privileged access (no push, pull request, publishing, deployment or sending); its output is the final report, commits on the working branch, or a shared location the task names. Label the description `Worker:`, `Crew:`, `Review:` or `Planning:`.
- **`wf-` prefix**: Templates stating an obligation that blocks acceptance rather than a process that proceeds conventionally carry a `wf-` prefix.
