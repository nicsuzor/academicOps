# Cross-surface observability

Cross-surface observability lets the user inspect any unit of work across the task graph, trace store, container runtime, and session log archive by opening links or querying identifiers directly on the project's infrastructure, with no agent processing. It serves the user auditing how tasks were composed into a workflow from templates, how workers executed them, and how supervisors received reports, verified claims, and caught mistakes.

## User stories

### US-1 Trace workflow composition, execution, and supervision across surfaces

As the user, I want to open a task identifier, a session identifier, or a verdict identifier directly on the project's infrastructure without agent processing and trace how tasks were composed from workflow templates, how workers executed them, and how supervisors received reports and caught mistakes, so that I can audit any workflow from end to end across every surface.

- **AC-1.1** Given a task composed from workflow templates, when the user looks up the task identifier on the task graph or in the trace store, then both surfaces resolve the composing session, composition turn trace, and ordered list of workflow templates resolved during composition.
- **AC-1.2** Given a task claimed or executed by a worker, when the user looks up the task identifier on the task graph, trace store, container runtime, or session log archive, then each surface resolves the worker session, dispatching parent session, container identity, deliverable link, and harvested session logs through that task's correlation keys.
- **AC-1.3** Given a worker handback evaluated by a supervisor across any delivery route (subagent return, peer message, or task record), when the user looks up the task identifier on the task graph or in the trace store, then both surfaces resolve the verdict outcome, verdict identifier, evaluating supervisor session, and judged worker session, and for a rejected or revision verdict (`REVISE` or `FAIL`), resolve the resulting feedback message and replacement task.
- **AC-1.4** Given a session identifier, when the user opens that session in the trace store or queries the other surfaces, then the session view resolves every task composed, claimed, or mutated in that session, every in-session subagent, every spawned worker container session, every peer-session message hand-off, and every verdict rendered by or on that session.
- **AC-1.5** Given a verdict or claim identifier, when the user queries the trace store or task graph by that identifier, then the matching record resolves the evaluating supervisor session and turn trace, the judged worker session and report delivery span, the full judged report argument, the verdict and reason, and any downstream retry message or replacement task.

### US-2 Read complete turn, model, tool, skill, and hook execution in one trace project

As the user, I want every session across every execution surface to export complete, secret-scrubbed turn, model, tool, skill, and hook-decision spans into a single trace store project, so that I can read what any session received, reasoned, decided, and produced in one place without missing content on injected turns.

- **AC-2.1** Given telemetry emitted from any execution surface, when spans arrive at the trace store, then every span lands in the single `academicOps` project with queryable span attributes identifying the emitting service, surface class, host, and (for repository-bound work) canonical repository slug and checkout root.
- **AC-2.2** Given a completed turn triggered by direct user input, a channel message, a cross-session peer message, or a background notification, when the user opens the turn trace in `academicOps`, then the turn root span (`CHAIN`) carries non-empty `input.value` and `output.value` with the final assistant reply, and child `LLM` spans carry `openinference.span.kind = "LLM"`, model name, prompt/completion/total token counts, and secret-scrubbed prompt and completion message arrays (including any expanded skill instructions loaded during the turn).
- **AC-2.3** Given a turn in which tools execute, runtime hooks evaluate gates or inject context, or rule/verdict evaluations run, when the user inspects the turn trace, then every tool span (`TOOL`) carries secret-scrubbed input, output, tool name, and call ID, every hook action emits a child span recording the hook event, gate, decision, and injected or refusal text, and every evaluation span parents under the active turn root span in the same `trace_id`.

### US-3 Correlate upstream MCP service spans with the calling session

As the user, I want task-graph and container-dispatch MCP service calls to attach to the calling session's turn trace and session identifier, so that server-side reads, mutations, and container launches appear in the caller's waterfall without creating synthetic transport sessions.

- **AC-3.1** Given a client or worker session invoking an upstream MCP service directly or through a gateway, when the service handles the request, then the service span shares the caller's `trace_id`, parents under the caller's tool span, carries the caller's `session.id`, records the transport connection ID separately in `mcp.session_id`, and stamps `task.id` whenever the call targets a task.
- **AC-3.2** Given an MCP request arriving without an explicit client session identifier, when the service exports its span, then the transport connection ID is recorded in `mcp.session_id` and `session.id` remains unset.

### US-4 Observe live and exited worker containers across dispatch routes

As the user, I want to observe a worker container both while it runs and after it exits, whether launched through the container-dispatch service or an interactive host launcher, so that I can inspect container liveness, real-time output streams, active tool execution, and post-exit diagnostic logs.

- **AC-4.1** Given a running worker container, when the user inspects container state, tails container output, attaches to an interactive terminal session, or queries `academicOps` spans by `task.id` or `session.id`, then container liveness, unbuffered output events, and live turn, model, and tool spans are visible in real time.
- **AC-4.2** Given a worker container that exits cleanly or with an error, when container teardown finishes, then the container's session logs and transcripts are persisted under `<sessions_root>/logs/<date>/<task.id>/` and the container-dispatch span records `polecat.exit_code`, `task.id`, `worker.session_id`, and `parent.session_id`.

### US-5 Keep the trace store free of duplicate emitters and test noise

As the user, I want each surface traced by a single emitter and automated test runs isolated from the production trace store, so that session waterfalls, token totals, and project lists contain only real operational telemetry.

- **AC-5.1** Given any active client or worker session, when spans are exported to the trace store, then one canonical emitter per surface exports the session's turn, model, and tool spans with zero duplicate or redacted spans from secondary exporters.
- **AC-5.2** Given an automated test suite run, when tests execute tracer, hook, or service code, then zero test spans or temporary projects reach the production trace store.

### US-6 See where tokens went from the trace store's own cost views

As the user, I want every model call on every surface priced by the trace store from the spans themselves, so that I can see spend by session, task, agent, model, host, and surface in the trace store's own cost views, with no agent processing and no bespoke scripts.

- **AC-6.1** Given a model call on any surface, when its spans reach `academicOps`, then exactly one `LLM` span represents that call, carrying the provider's own model identifier in `llm.model_name`, `llm.provider`, `llm.token_count.prompt`, `llm.token_count.completion`, `llm.token_count.total`, and `llm.token_count.prompt_details.cache_read` and `cache_write`, so the trace store prices it from its model price table.
- **AC-6.2** Given a turn, session, or project total in the trace store, when the user reads it, then each model call's tokens are counted once: only `LLM` spans carry `llm.token_count.*`, and no `CHAIN`, `AGENT`, or `TOOL` span carries an aggregate.
- **AC-6.3** Given a token count the provider did not report, when the `LLM` span is exported, then it carries `llm.token_count.type = "estimated"`, so the user can separate measured spend from estimated spend.
- **AC-6.4** Given priced `LLM` spans, when the user filters or groups by `session.id`, `task.id`, `agent.name`, `host.name`, `aops.surface`, or `llm.model_name` in the trace store, then the cost views return that slice's spend directly.

## Design

### Hop-by-Hop Correlation Contract Across Surfaces (US-1, US-3, US-4)

Observability signals are persisted across four surfaces: the **Task Graph** (task records and frontmatter), the **Trace Store** (OpenTelemetry spans in project `academicOps`), the **Container Runtime** (Docker labels and live streams), and the **Session Log Archive** (harvested container logs on disk). Every hop in the driving user story is joined by explicit correlation keys on each surface:

| Starting ID      | Target entity                                  | Task Graph key                                                                                                        | Trace Store key (`academicOps` project)                                                                                                                                                                                                                                                                                                                                                                        | Container Runtime / Session Log Archive key                                                                                                                |
| :--------------- | :--------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`task.id`**    | **Composing session & workflow templates**     | `reified_by_session_id`, `reified_by_trace_id`, `workflow_templates`, `origin.session_id`, `origin.message_id`        | Composition turn and task-mutation spans with `task.id = <task.id>` carry `session.id`, `trace_id`, and `aops.workflow.templates` (JSON array of resolved template IDs)                                                                                                                                                                                                                                        | —                                                                                                                                                          |
| **`task.id`**    | **Worker session & container execution**       | `session_id`, `parent_session_id`, `container`, `branch`, `pr_url`                                                    | Dispatcher and worker spans with `task.id = <task.id>` carry worker `session.id`, `parent.session_id`, and `polecat.exit_code`                                                                                                                                                                                                                                                                                 | Container labels `polecat.task_id`, `polecat.session_id`, `polecat.parent_session_id`, `polecat.project`; logs at `<sessions_root>/logs/<date>/<task.id>/` |
| **`task.id`**    | **Supervisor verdict & mistake recovery**      | `verdict_id`, `verdict`, `verdict_session_id`; on replacement tasks `revises_verdict_id`, `revises_task_id`           | Verdict spans with `task.id = <task.id>` carry `verdict.id`, `claim.id`, `verdict`, `verdict.reason`, supervisor `session.id`, `worker.session_id`, and `worker.span_id`; retry spans carry `revises.verdict_id`                                                                                                                                                                                               | —                                                                                                                                                          |
| **`session.id`** | **Session turns, model calls, tools & hooks**  | —                                                                                                                     | All spans with `session.id = <session.id>` (grouped in the Sessions view, one `trace_id` per turn)                                                                                                                                                                                                                                                                                                             | Harvested log/transcript files keyed by `<session.id>` under `<sessions_root>/logs/<date>/<task.id>/`                                                      |
| **`session.id`** | **Tasks composed, claimed, or mutated**        | Tasks where `reified_by_session_id`, `session_id`, `origin.session_id`, or `verdict_session_id` equals `<session.id>` | Client and MCP service spans in `session.id = <session.id>` where `task.id IS NOT NULL`                                                                                                                                                                                                                                                                                                                        | Container label `polecat.session_id = <session.id>` paired with `polecat.task_id`                                                                          |
| **`session.id`** | **Spawned workers, subagents & peer sessions** | Tasks where `parent_session_id = <session.id>`                                                                        | Subagents: shared `session.id` plus `agent.id`, `subagent.id`, and `parent.span_id` (spawning tool call `span_id`). Worker containers: parent dispatch span carries `worker.session_id`; worker spans carry `parent.session_id = <session.id>`. Peer sessions: sender message `TOOL` span and receiver turn `CHAIN` root span share `aops.team`, `aops.message.id`, `aops.message.hash`, and `peer.session_id` | Container label `polecat.parent_session_id = <session.id>`                                                                                                 |
| **`session.id`** | **Verdicts rendered by or on the session**     | Tasks where `verdict_session_id = <session.id>` or `session_id = <session.id>`                                        | Verdict spans where `session.id = <session.id>` (as supervisor) or `worker.session_id = <session.id>` (as judged worker or peer)                                                                                                                                                                                                                                                                               | —                                                                                                                                                          |
| **`verdict.id`** | **Supervisor session & turn trace**            | Task record with `verdict_id = <verdict.id>` carries `verdict_session_id`                                             | Verdict span with `verdict.id = <verdict.id>` (or `claim.id = <claim.id>`) carries supervisor `session.id`, `trace_id`, and `parent_id` (turn root span)                                                                                                                                                                                                                                                       | —                                                                                                                                                          |
| **`verdict.id`** | **Judged worker session & report text**        | Task record with `verdict_id = <verdict.id>` carries worker `session_id` and `## Report`                              | Verdict span carries `worker.session_id`, `worker.agent_id`, `worker.span_id`, `task.id`, and the judged report argument in `input.value`                                                                                                                                                                                                                                                                      | Logs for `task.id` in `<sessions_root>/logs/<date>/<task.id>/`                                                                                             |
| **`verdict.id`** | **Mistake-recovery retry or replacement task** | Follow-up task where `revises_verdict_id = <verdict.id>` and `revises_task_id = <task.id>`                            | Subsequent feedback message, dispatch, or task-creation span where `revises.verdict_id = <verdict.id>`                                                                                                                                                                                                                                                                                                         | Replacement worker container labelled with the new task's `polecat.task_id`                                                                                |

### Span Attribution and Telemetry Invariants (US-1, US-2, US-3, US-4, US-5)

In addition to the hop correlation keys above, spans in `academicOps` satisfy the following attribution and completeness invariants:

| Attribute / Invariant                                                                                                       | Requirement and Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| :-------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Single project (`openinference.project.name = "academicOps"`)**                                                           | Every emitter sets `openinference.project.name` and `project.name` to `"academicOps"` (US-2). Partitioning traces across per-directory, per-worktree, or per-service projects breaks cross-surface waterfalls and single-project queries.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Emitter, surface, host, and repository (`service.name`, `aops.surface`, `host.name`, `aops.repo`, `project.dir`, `cwd`)** | Every stored span exposes non-null `service.name` (identifying the emitting component: `aops-claude-hooks`, `aops-agy-hooks`, `aops-verdict-hooks`, `pkb`, or `polecat-mcp`), `aops.surface` (identifying the execution surface class: `claude-code`, `agy`, `github-actions`, or `mcp-server`), and `host.name` (hostname, container ID, or CI runner ID) directly in queryable span attributes (US-2, US-4). Repository-bound spans also carry `aops.repo` (canonical repository slug with aliases normalized), `project.dir` (checkout root), and `cwd`. When running in CI, spans attach `github.repository`, `github.workflow`, `github.job`, `github.run_id`, `github.run_attempt`, `github.run_url`, `github.sha`, `github.ref`, and `github.event_name`. |
| **Session groupability and turn hierarchy (`session.id`, `agent.name`, `agent.id`)**                                        | Every span belonging to a session carries the same 36-char dashed UUID in `session.id`, plus `agent.name` (role slug) and `agent.id` (session UUID for trunk, invocation ID for subagents) (US-1, US-2). Each turn creates one trace with a `CHAIN` root span, and all model (`LLM`), tool (`TOOL`), subagent (`AGENT`), hook-decision, verdict, and rule-evaluation spans in that turn share `trace_id` and parent under the turn tree. Keeping one trace per turn bounds waterfall size while `session.id` reassembles the whole session.                                                                                                                                                                                                                      |
| **Complete turn, model, tool, and skill payloads (`input.value`, `output.value`, `llm.*`, `tool.*`)**                       | Completed turn root spans carry non-empty secret-scrubbed `input.value` and `output.value` (the final assistant reply) whether triggered by direct input, channel message, peer message, or background notification (US-2). Child `LLM` spans preserve `openinference.span.kind = "LLM"` without attribute-limit eviction and carry `llm.model_name`, `llm.provider`, `llm.token_count.prompt`, `llm.token_count.completion`, `llm.token_count.total`, `llm.input_messages` (including expanded skill instructions when a skill is loaded in the turn), and `llm.output_messages`. Tool spans carry secret-scrubbed `input.value`, `output.value`, `tool.name`, and `tool.call_id`.                                                                              |
| **Hook decisions and verdict spans (`aops.hook.*`, `verdict.*`, `claim.id`)**                                               | Runtime hooks that inject context, arm or disarm a gate, or block/warn on an action emit a child span under the active turn carrying `aops.hook.event`, `aops.hook.gate`, `aops.hook.decision` (`"allow"`, `"block"`, `"warn"`, `"inject"`, `"arm"`, or `"disarm"`), and the injected or refusal text in `output.value` (US-2). Supervisor report evaluations across subagent returns, peer messages, and container task-record handbacks emit a verdict span carrying the correlation keys in the hop table above so every acceptance or rejection (`PASS`, `REVISE`, `FAIL`) is auditable from the trace store and task record alike (US-1).                                                                                                                   |
| **MCP service correlation (`mcp.session_id`, W3C `traceparent`)**                                                           | MCP gateways forward W3C `traceparent`, the caller's `session.id`, and active `task.id` to upstream MCP services (US-3). Upstream services parent their spans under the caller's tool span, populate `session.id` exclusively from an explicit client session ID supplied by the caller, record the transport connection ID in `mcp.session_id` so stateless calls never create synthetic sessions, and stamp `task.id` on task-targeted operations.                                                                                                                                                                                                                                                                                                             |
| **Worker container streaming and log archive (`polecat.*`, `<sessions_root>/logs/<date>/<task.id>/`)**                      | Worker containers stream unbuffered output events during execution for live inspection alongside live trace spans, and persist their internal CLI logs and session transcripts to `<sessions_root>/logs/<date>/<task.id>/` before container removal so diagnostic records survive container cleanup (US-4).                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Single canonical emitter and test isolation**                                                                             | Each surface is instrumented by one canonical emitter exporting complete, secret-scrubbed spans, with duplicate or redacted secondary exporters disabled once turn, `LLM`, subagent, and hook-parenting completeness hold (US-5). Automated test runs emit zero spans to the production trace store.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
