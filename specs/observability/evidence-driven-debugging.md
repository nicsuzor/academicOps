# Evidence-Driven Debugging

## The Problem This Solves

Ad hoc debugging has a characteristic shape: read source code, form a hypothesis, patch, check if it
works, move on. The fix gets made; the understanding dissipates. Next time something breaks in the
same area, you start over.

This compounds in agentic systems because:

- Sessions are short — context is lost between them
- Multiple agents work on the same codebase — no shared mental model
- Bugs that feel "fixed" resurface because the fix wasn't validated against all cases

The result is the same debugging work done repeatedly, with diminishing confidence each time.

## The Core Principle

**Investigation artifacts are infrastructure, not throwaway work.**

When you need to see what a system is actually doing, you build the minimal tool to see it. You use
that tool to produce your diagnosis. Then you commit it, because you will need it again.

By the end of a debugging session, you should have:

1. A tool that makes the bug visible
2. A fix validated by that tool
3. A test that uses the tool to prevent regression

You do not build the tool speculatively. You build it because you need it right now. But you build it
properly, because you know you'll need it again.

## The Antipattern: Separated Investigation and Infrastructure

The natural but wrong instinct is to plan debugging work in two tracks:

- Track A: investigate the bug (ad hoc — read code, form hypotheses, patch)
- Track B: build better tools for next time (speculative — built after the fact)

This fails for several reasons:

- Track A produces no durable artifacts. The diagnosis lives in your head, not the codebase.
- Track B gets deprioritised or built for a problem that no longer matches what you found.
- Future debugging sessions start from scratch again.

The correct structure collapses both tracks into one: **you build the tool in order to do the
investigation, and the tool stays**.

## The Workflow

### Phase 1: Instrument before you diagnose

Before reading source code to form hypotheses, ask: **what tool would let me see what's actually
happening?**

Build the minimal instrumentation:

- Logging at the decision point you care about (what was the input? what was the output? why?)
- Structured format (JSON lines preferred — machine-readable for later analysis)
- Committed to the codebase immediately

Then use the instrument to produce your diagnosis. The diagnosis must be evidence-based — it cites
log output or tool output, not code reading. Code reading is for understanding _why_ the evidence
shows what it shows, not for forming the initial hypothesis.

**Phase closes when:** the instrument is committed AND the diagnosis is written with evidence.

### Phase 2: Build a reproducer, then fix

Build a tool that reproduces the bug without a live session:

- A CLI command that exercises the system component under investigation
- Takes state as input (e.g. "what would the gate do for tool X in state Y?")
- Uses the real implementation — not a stub or reimplementation
- Exit code encodes the result (0/1) so it's scriptable

Use this tool to reproduce the bug first (confirm you can trigger it on demand), then fix the root
cause, then confirm the fix with the same tool.

**Phase closes when:** the reproducer is committed AND the fix is validated by the reproducer.

### Phase 3: Formalise into tests

Do not write tests from scratch. The instrumentation (Phase 1) and reproducer (Phase 2) already
contain everything:

- The reproducer becomes the test substrate — tests call it as a subprocess
- Test cases are the scenarios you already explored: the bug case (now fixed), the happy path, the
  edge cases (self-exemption, etc.)
- A coverage matrix is generated by running the reproducer across all known inputs — not maintained
  by hand

**Phase closes when:** the test suite is green in CI AND the coverage matrix is committed.

### Phase 4: Operationalise

Wrap the investigation artifacts into operational tooling:

- A **health check command** that shows current system state and recent log tail — the first thing
  anyone runs when something seems wrong
- A **CI contract** that runs on PRs touching the relevant code — diffs the coverage matrix,
  fails on regressions
- A **contract document** that describes what the system does, what a maintainer must preserve, and
  where the tools are

**Phase closes when:** a maintainer who didn't write any of this can understand the system from
the document alone.

## Decision Rules for Agents

**If you find yourself reading source code without any tool output:** stop. Ask what instrument
would let you observe the behavior directly. Build that first.

**If you built a throwaway script to investigate:** commit it instead. Throwaway scripts are just
undocumented tools.

**If you're writing tests after the fact:** check whether your reproducer (Phase 2) can serve as
the test substrate. It almost always can.

**If you're planning "infra work" as a separate track from "investigation":** collapse them. The
infra work IS the investigation.

**If a phase is "done" but has no committed artifact:** it is not done.

## How to Structure the Task Plan

Each phase of a debugging epic should be a separate task with a hard dependency chain. The template:

```
Phase N: [Build X] to [observe/reproduce/validate Y]
```

The title encodes both the tool being built and the investigation it enables. This prevents
drift — if the tool doesn't enable the stated investigation, the phase is not complete.

Each task body should specify:

1. What tool is being built (minimal viable spec)
2. What investigation it enables
3. What "done" looks like — both the committed artifact AND the finding

## What This Looks Like in Practice

Example: you suspect a hook gate is leaking (not blocking tools it should block).

**Ad hoc approach:** read hook code → find what looks like the bug → patch it → manually test a
few tools → ship it. Confidence: low. Next time it breaks: start over.

**Evidence-driven approach:**

1. Add gate decision logging (tool name, state, verdict, reason) → commit → run a session →
   read the log → produce a list of tools that leaked with timestamps as evidence
2. Build `gate simulate --tool Edit --state hydration_pending` → confirm it reproduces the leak →
   fix the root cause → confirm the fix with the simulator
3. Write tests that call the simulator: blocked tools fail when pending, allowed tools pass when
   complete, exemptions always pass → generate coverage matrix → wire into CI
4. Add `gate status` command → add CI path filter for hook PRs → write the gate contract doc

Confidence at end: high. Next time something seems wrong: run `gate status`, read the log, check
CI. Time to diagnosis: minutes.

## Reflection: How This Plan Was Developed

This workflow emerged from a planning session where the initial instinct was to create two separate
task tracks — one for investigating a specific bug (hydration gate leak), and one for building
observability infrastructure. The user correctly identified that this separation was wrong: it
creates an incentive for ad hoc investigation (because the real tools are on a different track) and
speculative infrastructure (because it's designed without the constraint of actual debugging need).

The restructured plan collapsed both tracks into phases where each phase builds a tool because it
needs it for that phase's investigation, and the tool stays. The test that a phase structure is
correct: does each phase produce both a committed artifact and a concrete finding? If a phase
produces only one, it's missing something.

The other useful heuristic that emerged: **if the gate fired but the tool ran anyway, that IS the
evidence.** You don't need to read the source code to know something is wrong — the observable
behavior is the diagnosis starting point.
