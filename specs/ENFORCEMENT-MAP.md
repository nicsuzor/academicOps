### 1.1 Per-message routing (agent-first)

Every hook message is enforcement **directed at the agent** — the **agent channel is non-negotiable and always present** (the `Agent template` column, which is the `CONTEXT_INJECTION` template the agent reads). What is _optional_ is whether anything also reaches the **user terminal**:

- **`silent`** — nothing rendered to the user; the agent handles it.
- **`same`** — the user sees the same text the agent sees (no separate template).
- **`[[file]]`** — a user-specific `USER_MESSAGE` template (the linked `*.policy_message` file).

**`Ephemeral→agent`** is the _target_ delivery discipline: push the full instruction to the agent **ephemerally** (transient) and leave only the **outcome + which hook fired** in the durable transcript. Supported today on agy (`injectSteps[].ephemeralMessage`, P✗); on Claude the `additionalContext` channel still persists (P✓), so its `✓` rows stay aspirational pending the Claude Stop-inject retirement ([`CLIENT-TRANSLATION.md`](CLIENT-TRANSLATION.md) P4) — **except `ida·reminder`, which is realised via the Claude Stop `asyncRewake` quiet-split** (full body → agent `<system-reminder>`, one-line summary → user; see the `✓ (asyncRewake)` cell and the capability caveat below). Channel wire-fields per client live in [`CLIENT-TRANSLATION.md`](CLIENT-TRANSLATION.md); this table owns the **disposition** (who-sees-what), not the wire mechanics.

> **Capability caveat — `Stop` user-surface dispositions on Claude (reopened & corrected 2026-06-29).** These dispositions are the **uniform design intent for every client**; there is deliberately no per-client variant. Where a client cannot currently honour one, that is a **capability gap, not intended divergence**. The precise gap: **no Claude/Gemini _user-SILENT_ (zero user output) agent-only `Stop` channel exists** — but "user-silent" was an over-strict reading of the requirement. The actual `Ephemeral→agent` target — _full instruction to the agent, one-line outcome to the user_ — **IS achievable on Claude 2.1.195 via the `asyncRewake` Stop hook** (config `asyncRewake:true` + `rewakeMessage` + `rewakeSummary`; fires on exit 2): decompiled (`Vic`) **and** PTY-proven (5 runs) to deliver the full body to the agent as a `<system-reminder>` while the user sees only a one-line `<summary>` (custom, or the default `Stop hook feedback`). **CAVEAT — delivery ≠ compulsion:** asyncRewake reliably DELIVERS with a quiet user surface, but the woken agent treats the reminder as advisory it weighs (it did NOT reliably act on it in testing, and correctly subordinates it to standing user instructions). So asyncRewake serves **quiet advisory Stop reminders** (e.g. `ida·reminder` — the biggest user-noise source), NOT a hard block: gates that must PREVENT stopping (`handover·block`, `qa·block`, `rbg_review·block`) still need `decision:block`+`reason` (forces resume, but shows the user the full reason). **WIRED (2026-06-29, PR #2020):** the `ida·reminder` warn path is now live — the Stop hook is registered with `asyncRewake:true`/`rewakeMessage`/`rewakeSummary` ([`aops-core/hooks/hooks.json`](../aops-core/hooks/hooks.json)) and the router emits the full `ida-reminder` body on stdout + **exit 2** when the advisory ida warn is the SOLE Stop contributor ([`router.async_rewake_body_for`](../aops-core/hooks/router.py)); the deleted `ida-policy-message` user line is replaced by the one-line `rewakeSummary`. ida is **fire-once per turn** (CLOSED→OPEN on Stop) so the next Stop produces no warn and the agent terminates — the re-wake cannot trap the session. Scope is strict: any other contributing Stop gate, or a DENY, falls through to the status-quo renderer; the block-class gates are untouched. **CORRECTION of the prior "Re-investigation closed (not achievable → relocate to `UserPromptSubmit`)" stamp:** that was wrong — it dismissed the whole goal on the user-SILENT technicality, and the `asyncRewake` mode was never tested (it was already present in the installed 2.1.195 binary). The `UserPromptSubmit`-relocation is demoted from "the remaining fix" to **one option for warn-mode gates that must let the agent actually stop**. The other open candidate — `hookSpecificOutput.additionalContext` without a block — _did_ change across versions (rejected on 2.1.158 → delivered on 2.1.191+) and renders `Stop hook feedback:` to the user (official Claude docs wrongly say it is not displayed). **Open design fork (Nic):** route the block-class Stop gates through `asyncRewake` (quiet delivery, paired with the existing block for enforcement) vs. keep the status quo — still open; this PR wires ONLY the advisory `ida·reminder`. Empirical capability cells live in [`CLIENT-TRANSLATION.md`](CLIENT-TRANSLATION.md); version-by-version + PTY evidence in [[kb-fcc2b95c]]; incident RCA in [nicsuzor/academicOps#2014](https://github.com/nicsuzor/academicOps/issues/2014).
>
> **Out of scope:** `SUBAGENT_INSTRUCTION` templates (`enforcer.context`, `qa.context`, `enforcer.audit`, `rbg_review.context`) reach **neither** the user nor the main agent — they are written to the temp file a _dispatched_ subagent reads. No user/agent disposition applies.

## 2. Capability & Identity Restrictions (Tool Access)

Tool and identity restrictions serve as foundational enforcement mechanisms, restricting what agents can do based on their role.

| Restriction Area                       | Enforcement Rule                                                                                                                                              | Applied To                                    |
| :------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------ | :-------------------------------------------- |
| **Specialized Execution (Playwright)** | Playwright and heavy e2e testing tools are strictly gated to specialized validation agents (`marsha`), enforcing separation of authoring vs QA.               | Excludes: `junior`, `pauli`, `rbg`            |
| **PKB Knowledge Write**                | While baseline agents (`junior`, `pauli`, `james`, `marsha`, `rbg`) share `mcp__plugin_aops-core_pkb__*` access, writes are constrained by `data-boundaries`. | Enforced via `rbg` review & `data-boundaries` |
| **Baseline Tooling**                   | Universal access to `Bash`, `Edit`, `Grep`, `Read`, `Skill` is granted across interactive (`junior`) and background workers to ensure `full-observability`.   | All Authoring Agents                          |

> **Note on Voluntary Skills (L3)**: Voluntary skills (e.g., `/verify`, `/design-rubric`, `/q`) are **capabilities, not enforcement mechanisms**. The restrictions on their use, and the hooks (like `qa` gate) that remind agents to use them, constitute the actual enforcement.
