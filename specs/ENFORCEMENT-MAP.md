### 1.1 Per-message routing (agent-first)

**Invariant: every gate verdict reaches the agent's context.** The agent channel is non-negotiable and always present — there is no gate whose verdict is agent-silent. What is a genuine per-gate CHOICE is whether anything _also_ reaches the user terminal (`silent` / `same` / `keep`); that disposition is a user-surfacing decision, not an enforcement one, and lives in [`specs/adhd/surface-contract.md`](adhd/surface-contract.md) § Gate user-visibility. Per-client wire capability (which field can actually carry a user-visible message) lives in [`CLIENT-TRANSLATION.md`](CLIENT-TRANSLATION.md).

## 2. Capability & Identity Restrictions (Tool Access)

Tool and identity restrictions serve as foundational enforcement mechanisms, restricting what agents can do based on their role.

| Restriction Area                                                       | Enforcement Rule                                                                                                                                                                                                                                                                   | Applied To                                                                                 |
| :--------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------- |
| **Specialized Execution (Playwright)**                                 | Playwright and heavy e2e testing tools are strictly gated to specialized validation agents (`marsha`), enforcing separation of authoring vs QA.                                                                                                                                    | Excludes: `ida`, `pauli`, `rbg`                                                            |
| **PKB Knowledge Write**                                                | `ida`, `pauli`, `james`, `marsha`, `rbg` don't own a PKB MCP server of their own, so all five use `mcp__plugin_aops-pkb_pkb__*`. Writes from that namespace are constrained by `data-boundaries`.                                                                                  | Enforced via `rbg` review & `data-boundaries`                                              |
| **Baseline Tooling**                                                   | Universal access to `Bash`, `Edit`, `Grep`, `Read`, `Skill` is granted across interactive (`ida`) and background workers to ensure `full-observability`.                                                                                                                           | All Authoring Agents                                                                       |
| **Command-Level Skill-Only Funnel**                                    | A slash-command's frontmatter `allowed-tools` is narrowed to `Skill` only, forcing every execution path through the delegated skill so the command file stays a thin wrapper with no independent tool surface (a chokepoint/funnel, L4).                                           | `dispatch.md`, `maintain.md`, `pull.md`                                                    |
| **Comment-Triggered Agent Identity Gate (GHA workflow, not a plugin)** | An `@claude` mention that would grant write/Bash access is restricted to `COLLABORATOR`/`MEMBER`/`OWNER` comment/review authors (`author_association`), matching `trigger-enforcer.yml`/`trigger-qa.yml`'s allowlist — an arbitrary commenter cannot invoke a write-capable agent. | `claude.yml` (`claude` job only — `claude-issue-triage` is read-only regardless of author) |

> **Note on Voluntary Skills (L3)**: Voluntary skills (e.g., `/verify`, `/design-rubric`, `/q`) are **capabilities, not enforcement mechanisms**. The restrictions on their use, and the hooks (like `qa` gate) that remind agents to use them, constitute the actual enforcement.

## Known gaps

- **Axioms are enforced reactively, not delivered always-on.** No hook injects the axiom set at SessionStart; no working agent `@`-imports `AXIOMS.md` — only `rbg` does (as its review reference, not "told to obey"). `.agents/CORE.md` restates `halt-on-failure`/`data-boundaries` operationally and carries the **universal safety floor** — Safety Invariants (no credential read/store/broker) + PKB-HALT — as the one injected copy for every surface, via the `@`-import (see the Safety floor row above). Coverage is verified per-surface: polecat workers' PKB-HALT floor is asserted by `tests/polecat/test_prompt_template.py::test_prompt_carries_pkb_halt_floor` (checks `PKB_HALT_FLOOR` reaches `build_polecat_prompt` output in both task and issue modes); interactive/in-repo-agent PKB-HALT coverage is the `.agents/CORE.md` prose itself (§ PKB-HALT), the one injected copy for that surface — no separate per-agent duplicate. The same pattern now closes the polecat leg of the `data-boundaries` gap: `test_prompt_carries_egress_guard_floor` asserts `EGRESS_GUARD_FLOOR` reaches `build_polecat_prompt` output in both modes, while the interactive leg remains the `.agents/CORE.md` `@`-import (§ PKB egress guard). Enforcement is the periodic `rbg` gate plus the per-rule rows in [Unified Matrix](#1-unified-ssot-matrix-rules-mechanisms-and-triggers).
- **Auto-mode classifier seeded and populated** (L5). The polecat `autoMode` ruleset (`polecat/defaults/claude-settings.json`) carries `environment`/`allow`/`soft_deny` entries — the individual rules are maintained directly in that file, not enumerated per-rule here or in the canonical spec, per the mechanism-class grain this map tracks. New rules still follow the evidence loop before landing. Canonical: [`auto-mode-classifier.md`](enforcement/auto-mode-classifier.md).
- **Hydration / commit gates**: env vars wired (`HYDRATION_GATE_MODE`, `COMMIT_GATE_MODE`) but no `GateConfig` body — stubs.
- **`rbg` threshold: a ruling to lower it was never implemented in code.** A prior redraft recorded a decision to lower the value from 50 to ~17; `aops-core/hooks/gate_config.py`'s direct-CLI fallback `_RBG_THRESHOLD_DEFAULT` and `polecat/defaults/polecat.yaml.example`'s `gates.rbg_threshold` both still ship **50** (verified against source). This map states the code-verified value; closing the gap needs either a code change or an explicit reversal of that ruling.
- **Evidence loop step 5** (recommendation synthesis within `/issue-sweep`) still leans on agent judgment per cycle rather than a scored model; capture (step 2 `/learn`), pattern detection + classification (steps 3–4, `/issue-sweep`), and implementation (step 6) exist and are in active use.
