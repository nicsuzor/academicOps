### PR review pipeline

The mechanisms that fire on a PR / at merge, and the manual routes that invoke the same agents off-pipeline. Same column shape as the axiom map above. Where a mechanism reviews **all** axioms (it is not keyed to one), `RULE` is the shorthand `Verify AXIOM compliance` rather than a per-axiom enumeration; where a mechanism reviews PKB design-intent rather than axioms, the rule names that instead (it is **not** an axiom check). The above per-axiom GitHub-PR rows that simply restated "PR push or `/review-pr` advises on axiom X" have been folded into the `Verify AXIOM compliance` rows here; the genuinely axiom-specific PR rows (`do-one-thing`/`exercise-authority` `PR push → warns change-author`; `halt-on-failure`/`data-boundaries` `PR merge attempt → blocks auto-merge`) remain in the axiom map. Each mechanism shows **both** its automatic trigger (the event/cron that fires it) and its manual route (the command/comment a human uses to invoke it). The **enforced** merge gate today (P4, verified 2026-06-09, ruleset `13762049`) is `enforcer-status` + `qa-status` + `admit-status` + the mechanical checks (Lint, Pytest); see the branch-protection row. `merge-prep-status` has been removed (replaced by `admit-status`); `alignment-status` is **intentionally advisory** (not in the ruleset, by design — [[pr-pipeline]] §6).

## Pyramid (L0–L7)

Rows are **mechanism categories** arranged as a **regulatory pyramid**: the vertical axis is severity/invasiveness (base = light, apex = coercive) and width at each tier is the volume/frequency of enforcement applied there (base wide = high-volume cheap mechanisms; apex sharp = rare severe mechanisms). A tier holds **multiple blocks** at the same coercion level. Axioms (rules) do **not** appear as pyramid rows — they are the _content_ L1 always-on mechanisms carry. For the Braithwaite responsive-regulation framing and escalation discipline → [`enforcement.md`](enforcement/enforcement.md) §4. Per-fire costs below are order-of-magnitude; combine with tier frequency for per-session totals.

| L  | Class      | Mechanism categories (multiple blocks per tier)                                                                                                                                                                                                                                                                                                                                                         | Per-fire cost                              |
| -- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| L0 | base       | **Authoring memory**: PKB notes · inline comments · doc-strings                                                                                                                                                                                                                                                                                                                                         | ~0                                         |
| L1 | base       | **SessionStart guaranteed reads**: agent persona · status strip · `session_env_setup` env vars · repo-local `.agents/CORE.md` (`@`-import, CWD-dependent). **NOT** `AXIOMS.md`/`HEURISTICS.md` — neither is SessionStart-loaded (`AXIOMS.md` is `@`-imported by `rbg` only); the plugin `aops-core/CORE.md` path is inert (no such file). See Known gaps.                                               | ~50–500 tok/session, prompt-cached         |
| L2 | base       | **Lifecycle context injection**: UPS hints · hydrator · Stop-hook reminders (IDA, QA-gate, handover-gate)                                                                                                                                                                                                                                                                                               | ~50–500 tok per event                      |
| L3 | base       | **Voluntary skill invocation**: `/verify` · `/design-rubric` · `/q` · `/pull` · `/learn` · others (agent opts in)                                                                                                                                                                                                                                                                                       | per-skill, agent decides                   |
| L4 | middle     | **Mechanical checks (deterministic, no LLM)**: pre-commit hooks · bridge guards · `aca_data_autocommit` · `fail_fast_watchdog` · `normalize_mcp_names` · `orchestrator_boundary` · `policy_enforcer` hard-deny · settings.json `deny` rules                                                                                                                                                             | 50ms–2s wall-clock                         |
| L5 | middle     | **Judgment per-action gate (LLM)**: CC auto-mode classifier — `soft_deny` (context-overridable block) · `hard_deny` (absolute) · `allow` carve-outs. The framework's only judgment mechanism that fires pre-execution on every call; verdict surfaces to the user, and a denial returns its reason to the agent as a tool result. See [`auto-mode-classifier.md`](enforcement/auto-mode-classifier.md). | ~20–800 tok per fire + tool-call latency   |
| L6 | tip        | **LLM-mediated review subagent**: `rbg` · `marsha` · `enforcer` subagent · `alignment`                                                                                                                                                                                                                                                                                                                  | ~1.5–3k tok + 5–30s latency                |
| L7 | tip (apex) | **Branch protection + merge AND-gates**: branch protection rules · `loop_detector` · `<agent>-status` AND-checks · project-owner / admin approval                                                                                                                                                                                                                                                       | merge-blocking, irreversible at the moment |

> **Base-tier note.** L1, L2, and L3 are **delivery channels**; within each, the instruction can be tuned across a wide insistence / urgency / visibility / salience / placement spectrum (see [`aops-core/skills/aops/references/enforcement-design.md`](../aops-core/skills/aops/references/enforcement-design.md) — "Within-class Insistence & Placement Spectrum"). "Escalating" a base-tier failure means walking that spectrum (louder → reasoned → relocated → propagated → structured) and propagating the instruction across every failing surface before moving to a heavier tier. Default to instructions; bias hard against new L5+ gates (§4 of [`enforcement.md`](enforcement/enforcement.md)).

## Known gaps

- **Axioms are enforced reactively, not delivered to agents always-on** (corrected 2026-06-03). No hook injects the axiom set at SessionStart, and no working agent `@`-imports `AXIOMS.md` — only `rbg` does, and that is the enforcer's reference copy (it judges _against_ the axioms; it is not "told to obey" them), not axiom delivery to working agents. Enforcement is the periodic enforcer gate (the `all axioms` row) plus the per-axiom tool-call / commit / PR rows below. `.agents/CORE.md` (CWD-dependent `@import`) additionally restates `halt-on-failure` and `data-boundaries` operationally. Whether individual agent personas restate other axioms in prose is unaudited and not relied upon by the enforcement model. QA tracker: `aops-98c7ce49`.
- **Hydration**: parent skip cascades to child; missing hydration/commit gate bodies.
- **Reactive**: PostToolUse on tool error is `planned` (Phase 2).
- **QA**: gate active (close-on-work-begin landed); requirements still freeform — verifier prompt reviews session narrative, no structured acceptance-criteria source yet.
- **Settings**: global/user rules unverifiable from this repo.
- **Auto-mode classifier is wired but unseeded** (L5 judgment per-action gate). The `autoMode` key is currently absent from `templates/aops-core.plugin.json` and the polecat copy carries empty arrays, so the installed rule set is effectively CC defaults — the per-axiom "PreToolUse (auto-mode classifier match)" rows above describe **design intent**, not currently-active enforcement. By deliberate decision (2026-06-04) **no behavioural rules are seeded**: the cheaper instruction rung is walked first (scope-discipline → worker sessions, gap `aops-98c7ce49`) and grep→PKB is gated on D5 (`aops-217ba56d`); a classifier rule is added only if measurement shows the instruction insufficient. Canonical design: [`auto-mode-classifier.md`](enforcement/auto-mode-classifier.md).
- **Evidence Loop**: Steps 4-5 (pattern detection) and Step 7 (auto-map update) partial/unbuilt.
- **Subagent enforcement**: gates and context injection skipped for `is_subagent` sessions — this is by policy, not a gap. See [`enforcement.md` Session scope](enforcement/enforcement.md#session-scope).
- **Design-intent / alignment review**: **partially live, advisory by design.** Pauli reviews PKB design intent off-GHA because GHA cannot reach the Tailnet-internal PKB MCP (pathology **P3** in [`pr-pipeline.md`](workflows/pr-pipeline.md)). The **queue surface** (`pr-pipeline.yml`'s `alignment-queue` job — posts `alignment-status: pending` on HEAD, files an `alignment:queued` issue per PR) is **LIVE**; the **host-side cron + polecat-pauli dispatcher** that drains the queue is **SPEC-ONLY** until it ships (tracked at the P6 follow-up — see [`pr-pipeline.md`](workflows/pr-pipeline.md) §6.2). **`alignment-status` is intentionally NOT in the branch-protection ruleset** — it is advisory by design (the human Env gate is the alignment decision point; alignment never blocks merge — see [`pr-pipeline.md`](workflows/pr-pipeline.md) §6, §7). The enforced merge gate today (verified 2026-06-09) is `enforcer-status` + `qa-status` + `admit-status` + the mechanical checks (Lint, Pytest); `alignment-status` is **not** in this list and must not be added without a deliberate spec change. The live alignment stand-in until the host dispatch ships remains the manual `/strategic-review --critic` skill. See the `Verify design-intent alignment` row above.
- **QA at the PR gate**: **resolved — LIVE.** `qa-status` (marsha) is a required gate in the active ruleset; `agent-qa.yml` + `trigger-qa.yml` exist (Phase 2 shipped). The manual `/verify` path remains for the dev session.
