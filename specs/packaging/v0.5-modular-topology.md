# v0.5 Modular Topology — Package Boundaries and Gate Disposition

## What this document is for

academicOps ships today as one core package that carries its own quality/process
enforcement machinery. v0.5 splits that into a core that enforces nothing
mechanically plus two optional plugins that carry the discipline for those who
want it.

This document states the resulting package boundaries and gives the
**per-file disposition of every hook and gate in the tree** — the punch list
each gate-move change works from. It exists so that no later change has to
re-derive where a file goes, and so that "did this land correctly?" is a
question with a written answer.

Doctrine is not restated here. The governing principle, the levers, and the
structural-prevention carve-out live in
[enforcement.md](../enforcement/enforcement.md); the gate mechanism's design
lives in [hook-gate-system.md](../enforcement/hook-gate-system.md). This
document applies that doctrine to package boundaries — it does not extend it.

## Target topology

Three packages replace the current two.

### `aops` — core

Carries PKB tooling and skills, the `/q`→dispatch workflow (hydrate → situate →
decompose → brief → dispatch → verify/handover), workflow assembly from
composable sources, the polecat dispatch flow, and the james / pauli / marsha /
rbg agents.

Core's enforcement contract: **workflow assembly + agent definitions +
structural prevention + trust that agents follow the workflow.** No face hooks.
No mechanical enforcement of quality or process.

Polecat's credential and container isolation **stays in core**. This is not an
exception grudgingly carved out of the zero-enforcement claim — the
zero-enforcement claim is scoped to quality and process, and isolation is
neither. It is structural prevention, the one sanctioned mechanical category.

### `jr/ida` — optional plugin

Face-only discipline for the interactive head, with whatever hook machinery that
discipline requires. Inherits the hook dispatch infrastructure, because after the
split the face is its only remaining consumer.

### `reflexes/cope` — optional plugin

Assembles rules from the universal axioms plus local project rules and applies
them at runtime via an on-device model or a configured LLM API.

**Binding constraint:** the model's output is an _overridable advisory consumed
by a deciding agent_, or the plugin is scoped to pure rule-assembly. It must not
emit an autonomous deny or block disposition. A binding deterministic verdict
that gates work is incompatible with the governing principle regardless of how
it is packaged — optionality purifies core, but it does not launder a gate.

### What does not move

`aops-tools/` is out of scope and unaffected.

## Classification vocabulary

Every file below is classified into exactly one of four dispositions:

|           | disposition       | meaning                                                                             |
| --------- | ----------------- | ----------------------------------------------------------------------------------- |
| **(i)**   | → `jr/ida`        | face discipline, or infrastructure whose only remaining consumer is face discipline |
| **(ii)**  | → `reflexes/cope` | axiom-derived policy assembly or advisory evaluation                                |
| **(iii)** | delete            | the concern is redundant, or discharged by a mechanism that survives                |
| **(iv)**  | stays in core     | structural prevention — credential/workspace isolation                              |

Two orthogonal properties determine the call, and the table records both so the
reasoning is legible rather than asserted:

- **Class** — is the file a _gate_ (produces a verdict), _infrastructure_ (the
  delivery mechanism itself, verdict-neutral), or _mixed_ (both concerns in one
  file)?
- **Concern** — is it quality/process (must leave core), cost/dispatch hygiene
  (must leave core), or credential/workspace isolation (stays)?

Infrastructure has no concern of its own. It follows its consumer. That is why
the gate plumbing lands in `jr/ida` rather than being deleted or kept: after
the process gates leave core, face discipline is the only thing still calling it.

Class and concern are reading aids, not inputs to a rule. The disposition of any
row is what its rationale argues, and a reader who disagrees with the rationale
should re-derive the disposition from it rather than read the columns as a
lookup table. Nothing downstream should key off these two columns — the moment
they are treated as the decision rather than a summary of it, the judgment they
are supposed to expose has been quietly replaced by a taxonomy.

#### `router.py` must be split, not moved

`router.py` carries two unrelated concerns in one script, and they have opposite
dispositions. Moving the file wholesale in either direction is wrong:

- **`SessionStart` branch → (iv) stays in core.** This is the credential
  isolation: it disables personal SSH keys (`IdentityAgent=none`,
  `IdentitiesOnly=yes`, `IdentityFile=/dev/null`), rewrites `github.com` SSH
  remotes to HTTPS, clears any inherited credential helper, and installs a
  fail-closed helper emitting the bot PAT — all scoped to the session's
  `CLAUDE_ENV_FILE` and this process tree, never global. This is structural
  prevention by construction and is exactly what the carve-out protects.
  Moving it to an optional plugin would make credential isolation opt-in, which
  is the one thing the topology must not do.
- **`SubagentStop` / `UserPromptSubmit` / `PostToolUse` branches →
  (i) `jr/ida`.** These inject `honesty.md`, `hydrate.md`, and `verify.md`
  respectively — face discipline, delivered as non-blocking context. (`router.py`
  has **no** `Stop` branch; `handover.md` is injected on Stop by the
  `exit_reflection_reminder` gate, not here.) Nothing in these branches produces a
  verdict; it is the reminder channel.

The split leaves core with a SessionStart-only credential-isolation entry point
and hands the injection branches to the face plugin. Both halves keep the
Antigravity/Claude wire translation they already have.

## Findings that change the downstream work

Three things turned up while classifying that alter the risk and shape of the
moves. They are recorded here because a later change that assumes otherwise
would be planning against a system that does not exist. **Finding 1 as first
written described a defect that has since been fixed on `dev`**; it is kept as a
corrected record because its downstream consequences were reasoned from the
now-false premise and had to be re-derived — the reversal matters more than the
original claim did.

### 1. The core gate pipeline was briefly dead — fixed on `dev`

For a window, `verdict.py` declared `Verdict` with a third field, `user_text`,
that had no default:

```
outcome: Outcome
inject_text: str
user_text: str | None   # no default
```

while `warn()` and `deny()` still constructed it with two arguments, so every
gate raised `TypeError`. Because `gate_dispatch._run_gate` isolates gate
exceptions and skips the offending verdict, the failure was silent — it went to
stderr and the hook emitted nothing. Both registered gates
(`require_subagent_model`, `exit_reflection_reminder`) return via `warn()`, so
both crashed.

**This is fixed.** PR #2311 (task `aops_cace51f9`, commit `622cb1198`, merged to
`dev` 2026-07-23) added the missing default; the current source reads
`user_text: str | None = None` and `warn()`/`deny()` forward it. Verified on
`dev`:

```
$ echo '{"hook_event_name":"Stop","session_id":"t"}' | uv run python aops/hooks/gate_dispatch.py claude
{"hookSpecificOutput": {"hookEventName": "Stop", "additionalContext": "<academicOps handover reminder>..."}}
$ uv run pytest tests/hooks/ -q
39 passed
```

Consequence for the topology — **the reverse of what the first draft recorded.**
The pipeline is live, so stripping the process gates out of core is a real
behaviour change, not a no-op: `require_subagent_model` and
`exit_reflection_reminder` fire today, and a strip wave removes working
reminders that must be re-homed in `jr/ida`, not dead code that can be dropped.
The design question the move should still ask — does each gate earn its place? —
stands on its own merits; it is no longer propped up by the (false) claim that
these gates never successfully fired.

### 2. Merge order vs PR #2306, re-derived against the live pipeline

The `verdict.py` default is already fixed on `dev` (Finding 1), independent of
PR #2306. So the sequencing question is narrower than the first draft framed it:
#2306 no longer flips the pipeline from _dead_ to _live_ — that already
happened. What #2306 (still open) adds is a new **fail-closed `deny` gate**,
`require_aops_bot_gh_token`, landing on an already-live pipeline.

The live question that remains: if #2306 merges before the gate-strip wave, a
blocking deny gate starts firing on push commands, and the strip wave then has
real blocking behaviour to preserve or relocate deliberately. If the strip /
redirect happens first, that gate never lands in core at all. Either order is
workable; they are not equally risky, and the order must be decided rather than
discovered.

### 3. `require_aops_bot_gh_token` has the right concern and the wrong shape

Its classification as core is on the merits — credential isolation, not process.
But the implementation is in tension with the doctrine it is protected by:
structural prevention is _prevention by construction_, "never reactive
detection, never content-sniffing." This gate is reactive detection by substring
match on command text:

```
_PUSH_COMMAND_MARKERS = ("git push", "gh pr create", ...)
is_push_op = any(marker in cmd for marker in _PUSH_COMMAND_MARKERS)
```

That is bypassable by ordinary means (`git  push` with two spaces,
`git -C dir push`, aliases, a shell variable, any non-Bash tool) and it inspects
command content, which the doctrine's mechanical layer is not supposed to do.

The durable fix is to move the guarantee to construction: make the SessionStart
isolation unconditional, so that an absent `AOPS_BOT_GH_TOKEN` produces a
session in which no credential can authenticate to GitHub at all, rather than a
session that pattern-matches for push commands after the fact. Then the gate is
redundant and can go.

Recorded as **(iv) stays in core, rework required** rather than
**(iii) delete**, because deleting it before the SessionStart path fails closed
would open the exact gap it covers.

Also mechanical: it imports `from gates.event import Event` (absolute) while
`registry.py` imports it relatively. The two styles resolve differently
depending on entry path; one of them is wrong.

## Applying this table

**Resolve the destination before applying any row.** The table states where each
file's concern belongs, not where it physically goes — and neither target package
exists yet. There is no `jr/ida` package (only `aops-jr/`, whose rename is
deferred below) and no `reflexes/cope` scaffold at all. The first step of the
first move is therefore to settle the target paths and create them; a change that
starts by reading a disposition off this table will stall immediately.

Every change that moves, deletes, or reshapes a file in this table updates
[enforcement.md](../enforcement/enforcement.md) in the **same** change, per
[RULES.md](../../.agents/rules/RULES.md#enforcement-map-currency). The
enforcement map is core doctrine and a move that leaves it stale is incomplete —
a reviewer should refuse the change, not file a follow-up.

`enforcement.md` is already stale against the tree in three ways that these
updates should correct. The last is the most consequential and the easiest to
miss:

- It names the injected templates `ida-hydrate.md` and `ida-reminder.md`. The
  files are `hydrate.md`, `handover.md`, `honesty.md`, and `verify.md`.
- It claims the router "injects two static templates, unconditionally,
  identically, on every surface — no per-client branching". It injects them per
  event branch — `hydrate.md` on `UserPromptSubmit`, `honesty.md` on
  `SubagentStop`, `verify.md` on `PostToolUse`, with `handover.md` on `Stop` from
  the `exit_reflection_reminder` gate — not two identical injections.
- **It does not document `SessionStart` or `PostToolUse` at all.** Its event list
  omits both. `SessionStart` is where the credential isolation actually happens —
  so the enforcement map is currently silent on the one mechanism this document's
  entire structural-prevention category depends on. Correcting only the template
  names leaves that gap open.

## Deliberately deferred

Named so they are not mistaken for oversights:

- **Package naming.** `aops-jr` currently carries both polecat dispatch and the
  face personas; after the split "jr" no longer implies dispatch. The rename is
  cheap and is settled when the moves are made, not here.
- **Relocating polecat dispatch into core.** In scope for the topology, but it
  is live machinery with its own in-flight rework; this document states only
  that dispatch belongs in core, not how the relocation sequences.
- **Marketplace and install ergonomics** for the two optional plugins.
- **Version strategy.** The split is breaking; a major bump is indicated, with
  no compatibility shim and no guided upgrade path.
- **Doctrine source consolidation.** Once this lands there must be one canonical
  statement of the enforcement model rather than two.
