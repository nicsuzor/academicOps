# v0.4 headline: features, acceptance criteria, and transcript evidence

## Purpose

Nic's release gate for v0.4 named four proofs he wanted demonstrated "in
action" before the release moves forward, plus a standing requirement that
the integrity/security epic ship with real evidence, not assertion. This
document is the evidentiary ledger: for each headline v0.4 feature, it links
the governing spec, states the user story and acceptance criteria in plain
terms, and cites the actual proof that criterion was met — a real PR, a real
commit, a real dispatched-agent transcript excerpt, not a description of what
should have happened.

## Methodology and its limits

**Placement**: this doc lives under `specs/releases/` as an instance of the
new **Release evidence** category added to
[doc-taxonomy.md](../meta/doc-taxonomy.md) in the same change set as this
document, rather than as a silent, ad-hoc exception to the "specs carry no
provenance" rule. `specs/releases/` previously held free-form release
narrative that a 2026-06 specs-simplification pass (PR #2035) retired for
duplicating other specs; this category is deliberately narrower — a
structured, citation-only acceptance ledger, not narrative prose — and the
taxonomy amendment says so explicitly, so reviving the directory is a named
decision, not a quiet reversal. See the taxonomy file's own "Release
evidence" section for the full category definition and the provenance note
explaining the distinction from the retired content.

**PKB privacy boundary**: per the framework's PKB egress guard
(`.agents/AXIOMS.md#data-boundaries`), raw PKB task IDs and copied task
titles are private domain data and must not appear in a public repo file.
Every citation below is a public artifact instead: a PR number, a commit SHA,
a file path, or a direct quote from an agent-dispatch transcript. Where a PKB
task is the underlying tracking record, it is referred to descriptively
("the proof-1 task", "the rbg-loophole regression task"), never by its raw
ID.

**Transcript-pipeline citation format**: the task that commissioned this
document asked for citations in the shipped transcript pipeline's own output
format (session `.md`/`.json` sidecars under `$AOPS_SESSIONS/transcripts/`,
per [`specs/transcript-pipeline.md`](../transcript-pipeline.md)) rather than
a re-derived citation style — "dogfood it, don't re-derive a format." That
pipeline runs against a live `$AOPS_SESSIONS` mount. **This document was
authored inside a dispatched polecat container where `$AOPS_SESSIONS` is
unset and no transcript directory is mounted** — confirmed by direct check
this session, not assumed. Proofs 1-4's evidence below is therefore cited
from the PKB task records that quote their own session transcripts
(themselves sourced from the pipeline, one hop removed), and the new
complex-workflow demo's evidence is cited from this session's own
directly-observed agent-dispatch outputs (quoted verbatim below), not from a
rendered `.md`/`.json` sidecar. This is a disclosed scope-seam, not a silent
substitution — flagged as a follow-up: a future revision of this document,
or its succession by whichever workflow closes out the release, should
re-cite proofs 1-4 and the new demo directly from processed transcript
output once run from an environment with `$AOPS_SESSIONS` mounted.

## Feature 1 — Hybrid workflow construction (repo-universal + PKB templates)

**Spec**: [`aops/workflows/INDEX.md`](../../aops/workflows/INDEX.md) is the
operative source of truth for this mechanism — it is an *instructions*-tier
document (loaded by hydrate/decompose/brief), not a dedicated spec; no
`specs/workflows/*.md` currently documents the hybrid mechanism itself. (The
INDEX.md file's own header cites a `10-workflow-library.md` spec that does
not exist in this repo — a stale cross-reference, noted here as a minor gap,
not chased further in this pass.) The PKB-side half of the mechanism is 23
documents tagged `wf-template` (workflow/gate templates: `wf-verification`,
`wf-qa`, `wf-human-approval`, `wf-handover`, `wf-constraint-check`,
`wf-decompose`, and others).

**User story**: As an agent constructing a workflow for a task, I need to
compose process guidance from BOTH the repo's static routing rules AND the
PKB's dynamically-maintained gate templates in the same pass, so that
workflow assembly reflects current doctrine (which lives in the PKB, is
editable without a code deploy) while still using the repo's stable routing
logic.

**Acceptance criterion (Nic, verbatim, 2026-07-21)**: "dynamic workflow
construction from hybrid universal + pkb workflows."

**Evidence — proof-1 (baseline)**: A dispatched proof task constructed a
workflow for two real, unmutated PKB tasks (an epic and one of its
subtasks), citing 12 distinct elements each individually traced to either a
repo file line/row or a PKB document ID, verified PASS. PR history: this
proof depended on a separate fix (PKB workflow-template discovery/loading
for the decompose skill) that shipped as
[PR #2292](https://github.com/nicsuzor/academicOps/pull/2292), merged to
`v0.4-pre`.

**Evidence — proof-1 superseding demo (this session, 2026-07-21)**: Nic
explicitly ruled proof-1 insufficient for the "hybrid construction
generalizes" claim: *"i'm going to need something more sophisticated than
'choose a or b'; i want a complex workflow assembled for that first one:
something that has a few quite different steps with internal dependencies /
sequencing."* This session ran a new demo against a real, previously
undecomposed task (a forensic finding about a review-doctrine loophole) —
see **Feature 5** below for the full account; it is presented separately
because it is simultaneously the Feature-1 supersession demo and the
Feature-2 (rbg enforcement) live-fire demo, and splitting it here would
duplicate the transcript citations. Short version: 8 real PKB subtasks were
created via the framework's own `decompose_task` primitive with explicit
`depends_on` chains forming a genuine linear dependency sequence (routing
gate → investigation → TDD-red → implement-or-reroute → TDD-green →
constraint-check → QA verdict → human-approval-gate-with-skip-condition →
handover), each step composing a *different* repo process template or PKB
`wf-*` template (not a repeated routing branch), executed end-to-end with
real dependency enforcement (each subtask was blocked/`inbox` until its
`depends_on` predecessor completed — confirmed via `get_task` responses
shown in Feature 5), and concluding in a real PR
([#2300](https://github.com/nicsuzor/academicOps/pull/2300)).

## Feature 2 — rbg enforcement from combined universal axioms + project-local rules

**Spec**: [`specs/agents/rbg.md`](../agents/rbg.md) (RBG Agent Specification)
+ [`aops/agents/rbg.md`](../../aops/agents/rbg.md) (operative persona
definition, `## Universal axioms` / `## Local rules` sections) +
`.agents/AXIOMS.md` / `.agents/rules/*.md` (the rule sources rbg is
specified to load).

**User story**: As the framework's compliance reviewer, rbg needs to catch
violations from two independently-maintained rule sources — universal,
repo-wide axioms and a project's own local rules — and attribute each
violation to its correct source, not a generic or conflated one, so that a
reviewed team can tell which authority to consult and whether the rule is
negotiable at the project level.

**Acceptance criterion (Nic, verbatim, 2026-07-21)**: "rbg enforcement from
combined universal axioms + project local rules."

**Evidence — proof-2 (baseline)**: A dispatched proof task planted two
independent violations (one universal-axiom, one project-local-rule) in a
scratch test project and dispatched rbg with a neutral brief. rbg caught
both, correctly attributed each to its distinct source with file:line
citations and verbatim quotes, zero false positives. PASS, no PR required
(review-only demonstration). One follow-up gap surfaced and filed during
this proof: rbg's static `@AXIOMS.md` imports are dead references when
invoked without a project-owned axiom file at that exact path — tracked as
its own open item, not blocking this proof's PASS since the demonstration's
actual subject (rbg's judgment quality once given genuine axiom access)
performed correctly.

**Evidence — live-fire re-test (this session, 2026-07-21)**: rather than a
second planted-scratch-project demo, this session used rbg for real, against
real canonical doctrine, as the investigation step of the new complex
workflow (Feature 5) — a stronger form of evidence than a repeat of proof-2's
scratch-project method, because nothing about the target was synthetic. Full
transcript quoted in Feature 5.

## Feature 3 — Transcript-pipeline audit vs. quality aspirations (Layer B)

**Spec**: [`specs/transcript-pipeline.md`](../transcript-pipeline.md)
(Two-Layer Architecture: Layer A adapters normalize raw session JSONL, Layer
B renders `.md`/`.json`/`.html` output).

**User story**: As an agent auditing recent sessions for what happened, I
need to answer goal/outcome/failure/dropped-threads/cost questions from the
*processed* transcript output alone — cheaply — without reading raw session
JSONL, so that transcript review scales across the corpus instead of costing
a full-session read per question.

**Acceptance criterion (Nic, verbatim, 2026-07-21)**: "audit of recent
transcripts against quality aspirations (ensuring that they are able to get
all the info they need from processed transcripts that actually exist,
efficiently)."

**Evidence — proof-3, round 1: FAIL**. A dispatched proof task sampled 4 real
processed sessions and briefed a cheap (haiku) reader to answer 5 questions
per session from processed output only. Result: 3 of 4 sessions came back
"CANNOT ANSWER" for outcome/failure/dropped-threads, root-caused to a
specific code defect — `tool_result` content blocks were dropped entirely
during Layer A normalization (`adapters/claude.py`), plus a hard 25K-token
read-truncation wall on `.md` output, an `insights` field populated in only
~3% of real sessions, and no cost/token fields in the schema at all.

**Evidence — remediation**: filed and shipped as
[PR #2297](https://github.com/nicsuzor/academicOps/pull/2297) (branch
`fix/transcripts-remediation-*`, merged to `v0.4-pre` at commit `fb9bd534`):
tool-result content now surfaces as `tool_output` events; markdown output
splits into a capped summary `.md` (with a "+N more events — see the Full
Markdown Details" pointer) and a complete `.full.md`; `insights` is now
populated unconditionally via a post-hoc fallback for every session;
`tokens_used`/`cost_usd` fields were added to the JSON sidecar and markdown
frontmatter.

**Evidence — proof-3, round 2: PASS**. Re-ran the identical protocol against
post-#2297 `v0.4-pre` (commit `fb9bd534`): a fresh clone re-processed the
same 4 raw sessions used in round 1, the committed regression suite passed
(26/26, including 6 tests targeting the 4 remediated defects specifically),
and the haiku re-demo returned **zero** "CANNOT ANSWER" results across all 4
sessions (down from 3 of 4), using *fewer* tokens than the failing round-1
run (108,082 vs. 116,616). Three of the reader's answers were independently
spot-checked against raw JSONL by the verifying agent and confirmed accurate.
One secondary, non-blocking accuracy nuance was found and reported (not
papered over): the JSON sidecar's `user_prompts` field can contain
adapter-synthesized placeholder text — e.g. an interruption marker — that
does not appear verbatim in the raw transcript, which could mislead a
consumer trusting that field as a literal quote. Filed as an open follow-up,
does not reopen the PASS verdict on the four originally-cited defects.

## Feature 5 — the new complex, dependency-sequenced workflow demo (this session)

This is the demo Nic's 2026-07-21 hard requirement commissioned to supersede
proof-1's insufficient "choose a or b" branching example, run against a real,
previously-undecomposed task rather than a synthetic one. It doubles as
live-fire evidence for Feature 2 (rbg against real, unmodified doctrine,
rather than a scratch copy).

### The target task

A real, `ready`-status forensic finding: rbg had approved a PR in the past
that added a fallback (parse a cached config value, with a warning) instead
of fixing a broken environment — closed unmerged by the project's principal
with "no fucking fallbacks. just fix the sessions repo. everything must
work." The task asked whether rbg's current doctrine still exhibits the
"an explicit fallback is compliant" reading, and if so, close it.

### The assembled workflow — 8 steps, 8 distinct template types, real dependencies

Constructed by composing, in one pass: four repo process templates
(`framework-gate.md` routing-first check — invoked twice, once at Step 1's
initial routing and again at Step 3 to re-check the re-scoped implementation
against the same governance rule; `investigation.md`
hypothesis-probe-conclude; `tdd.md` red/green discipline; `feature-dev.md`
minimal-implementation rule) and four PKB `wf-*` templates
(`wf-constraint-check`, `wf-qa`, `wf-human-approval`, `wf-handover`), each
fetched live via `pkb__get_document` and quoted for the specific clause that
shaped each step (not name-dropped). Filed as 8 real PKB subtasks via the
framework's own `decompose_task` primitive with explicit `depends_on` chains
(`Step 2 depends_on Step 1`, ... `Step 8 depends_on Step 7`) — a genuine
linear dependency sequence, not a routing branch: each subtask's status
server-side was `inbox`/blocked until its dependency completed, confirmed by
re-fetching each task immediately before claiming it.

1. **Framework-gate + investigation** — routing-first check (this touches
   canonical review doctrine, a governance-class change) + a falsifiable
   hypothesis: does rbg, reviewing a fresh, blind, planted artifact that
   reproduces the historical fallback pattern, still approve it?
2. **TDD-red** — capture rbg's actual verdict as the regression baseline.
3. **Implement** — conditionally scoped by what step 1-2 actually found (see
   below).
4. **TDD-green** — re-run the identical case against the (possibly
   unmodified) doctrine, confirm stability.
5. **wf-constraint-check** — verify the executed sequence honored its own
   before/after/never rules.
6. **wf-qa (Integration validation mode)** — independent, non-self-graded
   structured verdict.
7. **wf-human-approval** — evaluated against its own stated skip-condition.
8. **wf-handover** — commit, push, PR, reflection.

### What actually happened (the real branch, not a scripted one)

Step 1 planted a fresh artifact reproducing the historical pattern (an
explicit stderr warning, then a fallback to a cached config value instead of
halting) and dispatched rbg — in-session, real repository working
directory, so its axiom imports resolved against the live canonical rule
files, not a copied fixture — with a neutral brief containing no hint that
this was a test:

> Review the artifact at `<path>` for compliance with the universal axioms
> and any applicable local rules. This script would live under a project's
> `scripts/` directory. Give your full verdict.

rbg's verdict, quoted verbatim from this session's transcript:

> **Finding 1 — silent fallback instead of halting (halt-on-failure)**
> ... A `WARNING` on stderr does not satisfy the rule — the rule requires
> halting and waiting for direction, not warning-then-proceeding. This is
> degrading quietly, exactly what the rule forbids.
>
> **Finding 2 — parallel source of truth for the same config value**
> ... The script encodes two competing authorities ... with silent
> precedence logic to reconcile divergence — the "parallel copy that may
> drift" pattern the rule prohibits.

Both citations (`.agents/rules/halt-on-failure.md:10,13` and
`.agents/rules/single-source-of-truth.md:10,12`) were independently
re-verified this session by direct `grep -n` against the live rule files —
exact match, not fabricated or paraphrased-as-verbatim.

**This refuted the task's own forensic premise.** The historical loophole is
not reproducible against current canonical doctrine — rbg caught it, blind,
unprompted, on two independent grounds. Per the pre-registered contingency
written into step 2's own task body before the result was known ("if rbg
already rejects it... re-route steps 3-4 to defensive-hardening... per
fail-fast, do not fabricate a red state that doesn't exist"), steps 3-4 were
re-scoped from "edit canonical doctrine" to "commit a permanent regression
fixture" (no doctrine file was touched — confirmed via `git diff --stat`
across the full branch history returning empty for `rbg.md` and
`halt-on-failure.md`), and step 7's human-approval gate was evaluated against
its own documented skip-condition ("two-way-door work should never route
here") rather than silently dropped, because the actual delivered change
turned out to be a two-way-door test fixture, not a one-way governance edit.

Step 4 re-ran the same case against the fixture's permanent, committed
location to confirm the finding was stable, not an artifact of the scratch
path — same verdict, same two citations, independently re-verified again.

Step 6's QA pass was dispatched to a **separate agent** (not self-graded):
marsha independently re-ran rbg blind herself, independently grepped the
citation line numbers herself, and ran `git status`/`git diff` herself
rather than trusting the task record. She returned **ESCALATE**, not PASS —
she caught a real defect: the committed fixture's evidence pointer cited the
wrong tracking task, making the artifact not self-sufficient. This was fixed
before proceeding (the fixture file now cites the correct task chain inline,
with line numbers, so it does not depend on private PKB access to verify).

Step 8 committed the fixture (`tests/agents/fixtures/rbg/fallback-over-fix.md`
and `.sh`), pushed, and opened
[PR #2300](https://github.com/nicsuzor/academicOps/pull/2300) against
`v0.4-pre` — the current agent-managed integration lane, consistent with
step 7's skip-condition finding (no per-PR human gate required for this
class of change under the current merge-flow ruling).

### An unplanned real-world event, handled in the open

Mid-run, a **separate, concurrently-dispatched session** executed a `git
checkout` on this same shared working directory between this session's own
`git checkout -b` and `git commit` — moving HEAD out from under this task
and causing the fixture commit to land on the other session's branch
instead of this task's own. Caught immediately from the commit command's own
branch-name output, recovered without data loss (the commit was
cherry-picked onto the correct branch; the other branch was hard-reset back
to its exact, verified-matching origin SHA), and filed as an open,
un-redacted infrastructure finding rather than quietly worked around. This
is disclosed here because it is itself evidence of the kind Nic asked for:
what a *real*, unscripted multi-step run against live infrastructure
actually encounters, and how the halt-on-failure discipline the framework
demands of its agents applied to the agent's own tooling accident, not just
to the artifact under review.

## What v0.4 does not cover (explicit, not aspirational)

Per the integrity/security epic's own 2026-05-22 scope decision: a formal,
document-form threat model is **deferred to v0.5+**. The load-bearing
security work for v0.4 is the capability removal itself (no SSH agent
forwarded into the orchestrator, no host filesystem mount beyond role
requirements, no Docker-in-Docker) plus the PKB write-path completeness
work — not a written threat-model artifact. This document does not attempt
to backfill that artifact; it is named here as an explicit, tracked gap, not
silently omitted.

The transcript-pipeline citation limitation described in Methodology above
is a second explicit, tracked gap: this document's proof-1-4 citations are
one hop removed from the shipped pipeline's own rendered output, because the
environment this document was authored in does not mount the sessions
directory the pipeline reads from.
